# 外贸快查 · 产品出海市场地图（移动端）

一个手机优先的单页 Web 应用：**输入产品名 → 1 秒内看到「哪些国家要 / 为什么 / 用什么工具 + 投流还是自然流」**。
核心知识库随页面一起加载，**离线即可查询**（索引后单次查询实测 **0.007 ms 均值**，渲染 < 50 ms）；未收录的产品走
「品类池规则推断」，并可叠加本机服务端的联网搜索结果。

---

## 一、快速开始

```bash
cd D:\vibecoding\外贸数据查找

# 方式 A：纯静态（离线可用，联网兜底不可用）
#   直接双击 web/index.html，或用任意静态服务器托管 web/ 目录

# 方式 B：带联网兜底（推荐）
node server.mjs                 # → http://localhost:8787
# 手机访问：手机与电脑同一 WiFi，浏览器打开 http://<电脑内网IP>:8787
```

可选：接入商用搜索 API（不配则会自动降级到免 key 的 DuckDuckGo / Bing HTML 检索）

```powershell
$env:SEARCH_PROVIDER="tavily"        # tavily | serper | bing | searx | auto
$env:TAVILY_API_KEY="tvly-xxxx"
node server.mjs
```

重建知识库索引（改过 `web/data/kb.*.json` 之后执行）：

```bash
node tools/build-kb.mjs        # 合并 → 校验 → 生成 web/data/kb.bundle.js
node tools/selftest-engine.mjs # 引擎自测（命中率 / 边界 / 性能）
```

**技术选型理由（无框架）**：目标是手机浏览器打开即用、单次查询 < 1 s。
原生 JS + 同步加载的 KB bundle 省掉了打包器、路由与依赖下载，首屏一个请求即可查询；
纯前端计算保证响应时间与网络无关。服务端只承担「联网兜底」这一件前端做不了的事。

## 三、知识库数据结构

每条产品是一个对象，字段如下（所有 `kb.*.json` 都遵守同一 schema）：

```jsonc
{
  "id": "thermal-mug",                       // kebab-case 唯一 ID
  "name": "保温杯",                           // 中文主名
  "aliases": ["Stainless Steel Vacuum Flask", "Tumbler", "HS 9617"], // 英文名/别名/HS 编码
  "category": "家居园艺",                      // 分类
  "summary": "一句话定位，≤40 字",
  "markets": [                               // 4–6 个目标市场，按 rank 升序
    {
      "region": "欧洲",                       // 六大区之一
      "country": "德国",
      "rank": 1,                             // 推荐优先级
      "heat": 88,                            // 需求热度 0–100（知识库主观标定）
      "why": ["具体原因 30–60 字，可多条"],    // ← 回答"为什么这些地方喜欢"
      "channels": ["Amazon.de", "OTTO"],     // 该市场的主要触达渠道
      "entry": "切入建议 30–60 字",
      "risk": "风险/合规点 20–40 字"
    }
  ],
  "tools": [                                 // 5–8 个工具，按 priority 升序
    { "name": "Amazon Seller Central", "type": "B2C", "use": "怎么用", "priority": 1 }
  ],
  "adStrategy": {                            // ← 回答"投流还是自然流"
    "verdict": "双轨并行（前期投流测款 → 自然流做内容承接）",
    "paid": ["投流要点…"],
    "organic": ["自然流要点…"],
    "budget": "$800–1500/月",
    "kpi": "ACoS < 25%，首月转化率 > 8%"
  },
  "sources": ["Amazon Best Sellers - Travel Mugs", "HS 9617 贸易口径"],
  "confidence": "high | medium | low"        // 该条结论的可信度
}
```

**工具类型枚举**：`B2B / B2C / 社交 / 独立站 / 展会 / 数据`（覆盖 Facebook、LinkedIn、TikTok、Amazon、
Alibaba、Google Ads、Shopify、行业展会、海关数据等）。

**品类池（`kb.pool.json`）**：知识库未命中时的兜底模板，9 个品类（宠物 / 服饰 / 美妆 / 3C / 家居 / 户外 /
母婴玩具 / 汽配 / 工业机械），含关键词、区域优先级、why、渠道、工具、adStrategy 与 24 个国家参考。
命中的话结果标为 **规则推断（中等置信度）**，不冒充知识库结论。

## 五、联网搜索的接入方式

前端未命中知识库时，会先用规则立刻渲染结果，然后**异步**请求 `GET /api/search?q=产品`
（9 s 超时，失败也不会清空已渲染内容）。服务端 `server.mjs` 的适配链：

| 通道 | 环境变量 | 说明 |
|---|---|---|
| Tavily | `TAVILY_API_KEY` | 专为 LLM 设计的搜索 API，返回正文片段，质量最好 |
| Serper | `SERPER_API_KEY` | Google 结果镜像，量大稳定 |
| Bing Web Search | `BING_SEARCH_KEY` | 微软官方 API |
| SearXNG | `SEARX_BASE` | 自建实例，免费无 key |
| DuckDuckGo HTML | 无需 key | 默认兜底 |
| Bing HTML | 无需 key | 默认兜底 |

`SEARCH_PROVIDER=auto` 时按「已配置 → 免 key」顺序自动降级；任一通道成功即返回，全部失败返回
`{ ok:false, message:"联网检索全部通道失败…" }`，前端明确提示「本次结果仅来自本地规则推断，未使用联网数据」。

**服务端对搜索结果的加工方式（不做自由生成，避免编造）**：
1. 并发 3 组查询（英文、中文、`top importing countries HS code`），去重后取前 12 条；
2. 对标题+摘要做**确定性抽取**：国家名出现次数（≥2 次才计入）、信号词（进口增长 / 关税认证 / 平台格局 /
   需求走强 / 价格敏感 / 展会采购）；
3. 输出结构固定为「被提及频率 + 命中信号 + 原始链接」，并在 UI 标注
   **「该条由公开网页文本中出现次数统计得出，不代表市场规模或偏好强度」**；
4. 结果缓存 10 分钟。

> 实测：本机当前网络环境（无法直连 Google/Bing/DDG/Wikipedia）下联网通道会失败，UI 会明确提示，
> 不会用假数据填充——这是刻意设计的行为，不是缺陷。

## 六、结果如何区分「既有结论」与「联网信息」

| 徽标 | 含义 | 置信度 | 数据来源 |
|---|---|---|---|
| 🟢 知识库命中 | 产品在本地知识库中，结论为人工整理的市场判断 | high / medium / low（按命中方式与条目自带 confidence） | `web/data/kb.*.json` |
| 🟡 规则推断 | 未收录，用品类池或通用规则推导，只给方向 | medium（品类池）/ low（通用规则） | `kb.pool.json` + `rules.js` + `reference.js` |
| 🔵 联网补充 | 服务端检索到的公开网页信号，**以独立区块并列展示，不覆盖本地结论** | 未验证 | 实时搜索结果 + 原始链接 |

命中方式也会显示在 `matchedBy` 中：`exact / alias / contains / fuzzy / pool / rule`——
"模糊匹配"和"规则推断"会有明显降级提示。

## 七、响应速度

| 路径 | 实测 |
|---|---|
| 知识库命中 | 0.00–0.02 ms（纯内存索引查找） |
| 品类池推断 | 0.1–12 ms（首次正则编译） |
| 首屏可交互 | 一个 HTML + 5 个 JS/CSS 请求（KB bundle 约 253 KB，未压缩） |
| 批量基准 | 550 次查询 3.7 ms，均值 **0.007 ms/次** |
| 联网补充 | 3–15 s（取决于搜索通道；**异步追加**，不阻塞首屏结果） |

优化手段：同步加载 KB → 一次性建索引（名称 / 别名 / 核心名 / 品类四类键）→ 精确匹配优先、
包含关系次之、编辑距离最后；渲染用一次性 innerHTML 拼接；骨架屏在 requestAnimationFrame 后才让出主线程。

## 八、使用方法

1. 顶部输入框输入产品（中文、英文、别名都行），点「查询」或回车；
2. 三个页签：**① 国家市场**（点卡片展开原因/渠道/建议/风险）→ **② 偏好原因**（逐市场展开）
   → **③ 工具与流量**（投流 vs 自然流的结论、要点、预算、KPI 与工具清单）；
3. 右上 🕘 查看最近查询（本地 localStorage，最多 30 条）；
4. 结果底部「相关产品」可一键跳转同品类条目；「信息来源」列出该条目的依据；
5. 未收录产品会先出规则推断，随后自动叠加联网信息（有服务端时）。

## 九、局限与后续扩展

**已知局限**
1. `heat` 热度是**人工标定**的相对优先级，不是真实市场规模或交易额；接入 UN Comtrade / 平台官方数据前
   不要把它当财务依据。
2. 知识库为人工整理 + 联网核实，**不是逐国海关统计**；`confidence` 字段是自评，仍有主观性。
3. 免 key 的 HTML 检索在受限网络（如本机当前环境）不可用；生产环境请配 Tavily/Serper/Bing。
4. 中文输入依赖别名表与品类池关键词，长尾品名可能落到"通用规则"（低置信度）。
5. 联网结果只做**频次统计与链接引用**，没有做语义归属（无法证明"某国真的喜欢该产品"）。

**扩展方向**
- **接真实贸易数据**：UN Comtrade 公开预览接口已验证可用
  （`comtradeapi.un.org/public/v1/preview/C/A/HS?reporterCode=…&cmdCode=…&flowCode=M`），
  按 HS6 给每个国家算出"进口额/增速"，替换现在的 `heat`；
- **接平台侧数据**：Amazon / TikTok Shop / Shopee 类目榜单、Google Trends 区域热度；
- **知识库工程化**：把 `kb.*.json` 拆到 CMS 或表格维护，加 schema 校验 CI（当前 `build-kb.mjs` 已做基础校验）；
- **多语言**：结果可按目标市场生成本地语言版 listing 要点；
- **对比视图**：一次输入多个产品做市场重叠/差异化对比；
- **PWA 离线**：加 Service Worker 缓存，实现彻底离线安装（当前已加 manifest，SW 待补）。
